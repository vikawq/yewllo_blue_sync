950 LayerNorm fp32 仿真崩溃定位

2026-10-16 根因报告 _layernorm_fwd_kernel

根因有两层。直接原因在编译工具链：当单份 X tile 超过约 6.5 KB 时，triton-ascend 为 _layernorm_fwd_kernel 生成的代码里，某条向量 load 的 UB 地址操作数是从内存读出来的张量数据，而不是算出来的地址。生产之所以踩到它，是因为 TOKEN_BLOCK_SIZE_TABLE 只按 n_cols 选 BLOCK_SIZE_M，既不看 itemsize 也不看 BLOCK_SIZE_N，而出事的恰好是三者的乘积。

这比「崩溃」更严重：多数情况下它不崩，只是静默算错。abort 来自仿真器的对齐断言，真实硬件没有这道检查。同一份 kernel 换个输入数据，就能在 abort 与「跑完但结果错」之间切换。

影响面覆盖几乎所有生产配置：fp32 全部超线（1.8 至 4.9 倍），fp16 从 n_cols=256 起超线。只有 fp16 的 n_cols=128 在安全区内——最初「fp16 全部通过」的观察是被测 shape 恰好都在线内造成的假象。

边界已用 18 个有效数据点夹准，并有一组只改 n_rows 的决定性对照。尚未做的是反汇编，所以「为什么阈值在 6.5 KB」仍是现象层面的描述。

01

根因

第一层 · 直接原因 · 编译工具链

triton-ascend 为超过阈值的 tile 生成了错误的 UB 地址

kernel 源码与生产代码逐字一致，只有 constexpr 取值不同。tile ≤ 6.5 KB 时结果完全正确（X 全零时 max_abs_error = 0，bit-exact）；超过就必错。错的是那条向量 load 的地址操作数——它来自内存，内容是 X 的数据。

第二层 · 为何生产会踩到 · mojo_opset 启发式

TOKEN_BLOCK_SIZE_TABLE 对 dtype 和列宽都不敏感

layer_norm_fwd_heuristics 只用 n_cols 查表得出 BLOCK_SIZE_M。而决定生死的是 BLOCK_SIZE_M × BLOCK_SIZE_N × itemsize——表里既没有 itemsize 也没有 BLOCK_SIZE_N，于是每个 fp32 配置都落在阈值的数倍之外。

02

触发条件与边界

出错 ⟺ BLOCK_SIZE_M × BLOCK_SIZE_N × itemsize > 6656 B（6.5 KB）

上限取自实测的最大通过样本（BM=13, BN=128, fp32），最小失败样本是 7.0 KB，真阈值落在两者之间。与 dtype 本身、BLOCK_SIZE_M 的具体数值、是否 2 的幂、是否对齐到 32 都无关——只看三者的乘积。

行数只影响是否显形，不影响安全性

当 ceil(n_rows / BLOCK_SIZE_M) ≤ grid 时，每核最多跑一轮行循环，故障可能不出现。上图那三个空心点就是这种情况。

所以小规模用例通过不能作为安全依据——这一条值得写进测试规范，否则很容易得出「这个配置没问题」的错误结论。

n_cols ≥ 2048 的 fp32 即使 BLOCK_SIZE_M = 1 也超线（BN=2048 单独一行就 8 KB），单调 BLOCK_SIZE_M 救不了。原测试列表里 4096／8192 列都走 BN=2048，同属这一类。

同一张 TOKEN_BLOCK_SIZE_TABLE 还在另外三个文件里：npu/rmsnorm.py、npu/fused_add_layernorm.py、npu/fused_add_rmsnorm.py。后两个的 @triton.heuristics 是注释掉的，不吃这张表；rmsnorm.py 的训练前向 rmsnorm_fwd_impl 吃（表值 128 → 48，fp32 下 24 KB）。rmsnorm 这条线尚未在新脚本下测过。

04

修复建议

opset 侧 —— 立即可做，绕开问题

BLOCK_SIZE_M = max(1, 6656 // (BLOCK_SIZE_N × itemsize))
若 BLOCK_SIZE_N × itemsize > 6656，须先降 BLOCK_SIZE_N

约束必须同时管住两个块大小并把 itemsize 算进去。只按 itemsize 把表值砍半是不够的——那只对 n_cols=128 成立，n_cols ≥ 256 砍半后仍然超线。

代价是性能：n_cols=1024 的 fp32 从 BM=8 降到 1，行并行度降一个量级。所以这是止血，不是终局。

工具链侧 —— 真正的修复

需要向 triton-ascend 提单：同一份 kernel 源码，仅 constexpr 块大小变化，就会生成地址操作数取自张量数据的代码，且不报任何编译期错误。提单材料已齐：kernel 源码、各配置的 kernel.o、故障 PC 与地址、以及地址值可随输入数据变化的证据。

缺的一步是反汇编 kernel.o（对比 BM=13 正确与 BM=14 出错两份），指出那条 VLDI 的地址从哪来。仿真机上有 msobjdump，可以做。

测试侧

  • 精度测试不能只跑小 n_rows——行数不足会让这类故障完全不显形
  • 仿真用例的 timeout 设成 180 秒级别，挂死是常见形态，默认 3600 会白等一小时
  • standalone 脚本必须与生产 impl 逐字对齐，否则测的是生产里不存在的配置（附录 A）
05

证据

  1. 故障地址是从内存读出的 X 数据

    把崩溃报的 0x3EC7E035 转成小端字节序列，在仿真器 dump 出的输入 X_ptr.bin 里搜，唯一命中，byte_off=0x018714，即 X[195, 69]；W／B／args 全部 0 命中。按 randn 在该处的概率密度与 fp32 量化间隔估算，偶然命中概率约 0.036%。

    位置与分块几何吻合：BM=24 时 row_task_id = 195 // 24 = 8，tile 内局部坐标 (3, 69)，对应 pid=0 的第二次循环——与报错里的 id=2302（很早）一致。

  2. 换输入不换 kernel，地址跟着变

    BM输入致命 PC地址按 fp32 读
    24randn0x400173c0x3EC7E035X[195,69] = 0.390
    24全填 1.00x40018000x00000018常数
    24全填 0.00x40018000x00000018常数
    16randn0x4001e300x3EBEA9F30.372
    16全填 0.0不 abort—只是数值错

    数据不影响 codegen，所以同 BM 的几次是同一份 kernel.o。1.0 的位型 0x3F800000 虽越界但 32 字节对齐，只打非致命 overflow；0.0 的 0x00000000 完全合法——两次都越过了 0x400173c，死在后面另一个点。早期脚本把输入缩放 0.1 倍时，日志里的「地址」也随之缩小一个数量级（0.039 对 0.390）。

  3. 参数传递与 GM 布局没有问题

    mappings.tsv 与 abi.json 交叉校验：6 个 buffer 的地址、大小、页对齐全部正确，stride_x_row=128、n_rows=256、n_cols=128、eps 的位型也都对。所以问题在 kernel 内部，不在 host 侧传参。

  4. 地址值本身没有通用规律

    X 全填 0.0 时，BM=24 的故障地址是 0x18（＝24）、BM=18 的是 0x12（＝18），恰好等于 BLOCK_SIZE_M；但 BM=16 的地址若等于 0x10 同样不对齐、本该 abort，实际只是算错。(64,1024) BM=2 的地址是 0x2024，正好是 tile 大小 0x2000 加 36 字节。

    这些是各份编译产物的具体表现，不构成通用机理——这也是为什么还需要反汇编。

最初的 standalone 脚本有几处与生产 impl 不一致，已按 layernorm_infer_impl／rmsnorm_infer_impl 改正。这是为何修正前采集的数据不能与修正后的放在一起比较。

rmsnorm —— 走错了 kernel

rmsnorm_infer_impl 里 align() 是向上取整，所以 BLOCK_SIZE_N ≥ n_cols 恒成立，只有 n_cols > 10240 把它钳到 10240 时才会小于 n_cols。也就是说 n_cols ≤ 10240 一律走 _rmsnorm_infer_kernel_single（单次整行 load，W 在 row 循环外只 load 一次，BLOCK_SIZE_M 由 autotune 决定）。

而旧脚本一直在跑 _rmsnorm_infer_kernel 加表格 BLOCK_SIZE_M——生产里不会出现的组合。所以早期 rmsnorm 的全部结论（包括 fp32 (128,128) 输出全零）都不代表生产。weight 同样恒为 fp32；容差已按原测试改回 fp32 atol=1e-5／rtol=1e-6、半精度 3e-2／6e-3，参考实现用 F.rms_norm。

附录 C

仿真环境的两个坑

一、容器环境。两次 (64,*) 扫描是在没 source 过环境的容器里跑的，全部是编译期 OSError，仿真器一次都没启动——数据无效。探针脚本已加环境预检，并把异常分为 SIM／TIMEOUT／ACC／ENV 四类，ENV 不计入结论。另外仿真是 CPU-bound，多个 pem_davinci_standalone 并发会互相抢核、慢几十倍，必须串行。

二、torch_npu 元数据与编译缓存。容器里的 torch_npu 是为仿真环境手搓的 stub（__version__ = "2.6.0.fake"），不是 pip 装的，所以没有 dist-info。而 triton/backends/ascend/driver.py 的 NPUUtils.__init__ 会调 importlib.metadata.version("torch_npu") 给编译缓存做 key，缓存缺失时还会现场编译 npu_utils.cpp——那份源码 include 了 stub 里不存在的 C++ 头。平时能跑是因为缓存命中、不走编译。

这个故障与 LayerNorm 的问题无关，只是挡在前面。已有的 18 个数据点全部采集于它出现之前，不受影响。
