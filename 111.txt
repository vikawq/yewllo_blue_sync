三个问题都有明确答案，其中第 2 个的答案可能会改变你们的排查方向。

## 1. KV cache：**ND 分配、非量化，但写入走的是 PA_NZ 语义** —— 这里有一个真实的隐患

**分配和形状**：raw buffer 按 int8 字节分配，再 view 成目标 dtype（[model_runner_v1.py:4034-4048](vLLM-ascend_for_lingqu/vllm_ascend/worker/model_runner_v1.py:4034)），逻辑形状是 `(2, num_blocks, block_size, num_kv_heads, head_size)`（[attention_v1.py:101-108](vLLM-ascend_for_lingqu/vllm_ascend/attention/attention_v1.py:101)）——标准 ND paged 布局。**全仓没有一处对 KV cache 做 `npu_format_cast`**（grep 到的 `npu_format_cast` 全是权重和 MLA 的 wd_qkv/wu_q 之类）。

**量化：当前没开**。int8 KV（GQA-C8）路径确实存在——`_quantize_kv_to_int8` + `_prepare_c8_scales` + `_nz_5d_view`（5D NZ，内轴 32），但它挂在 C8 分支上，需要 `--kv-cache-dtype int8` 或 fa-quant 量化配置。你的启动脚本两者都没有，`--dtype auto` → KV = 模型 dtype，不量化。

**`VLLM_ASCEND_ENABLE_NZ=0` 管不到 KV cache**：这个开关的注释写得很清楚，是 "Whether to enable **weight** cast format to FRACTAL_NZ"（[envs.py:88-92](vLLM-ascend_for_lingqu/vllm_ascend/envs.py:88)），只影响 `w13_weight/w2_weight` 等权重。

**真正的问题在这里**：你们跑的是 A5/A6 适配器（A6 mock → `get_device_adaptor()` 返回 `A5DeviceAdaptor`），它的 KV 写入是——

```python
# vllm_ascend/device/device_op.py:791-802
class A5DeviceAdaptor(BaseDeviceAdaptor):
    @classmethod
    def reshape_and_cache(cls, key, value, key_cache, value_cache, slot_mapping):
        torch_npu.npu_scatter_pa_kv_cache(
            ...
            # A6 MOCK
            # cache_mode="Norm",
        )
```

`cache_mode="Norm"` 被**注释掉了**，标记就是 `# A6 MOCK`。于是 op-plugin 用默认 cacheMode → 发出去是 `PA_NZ` → runner 的真 CANN 报"PA_NZ cache 最后一维不合法" → 你们的对策是在 vAscend RPC 里把 `PA_NZ` 改写成 `Norm`（交接文档 4 阶段表 + 8.3 节）。

**这个改写只动了一个字符串属性，没有动数据布局，也没有动 tensor 描述符。** 客户端按 PA_NZ 的理解组织/看待这块 buffer，runner 按 Norm 执行 kernel，同一段字节被两种布局解释——**KV 内容会被搬错位**。而 `outputIndexes = {1,4}` 会把整块 cache 写回仿真侧，错误会固化在 cache 里，下一个 token 继续读错。这是"首 token 可见文本为空 / 数值不可信"的一个高置信度嫌疑点，优先级应该排在数值一致性验证的最前面。

另外注意：`_nz_5d_view` 是 `.view()` 不是 format_cast（[attention_v1.py:1441-1444](vLLM-ascend_for_lingqu/vllm_ascend/attention/attention_v1.py:1441)），它把 ND 分配的扁平 buffer 重新解释成 `(blocks, heads, D/32, block_size, 32)`——**元素顺序和 ND 不一致**，等于假定这块 buffer 物理上就是 NZ。所以 C8 路径一旦开启，同样的布局歧义会再来一遍。设计文档那边的约束是 `single_acl_format` + "无法证明 padding/blocked format 布局时拒绝生成该算子"（[integration_contracts.md:518,620](vAscend/docs/design/modules/real_calculation/integration_contracts.md:518)），你们的生产实现是绕过了这条闸门。

**该做的**：确认 op-plugin 对 `npu_scatter_pa_kv_cache` 默认 cacheMode 的取值，然后**两侧统一**——要么客户端显式传 `Norm` 并保证 buffer 是 ND（把那行注释放开），要么保持 PA_NZ 并让 runner 侧真的按 NZ 建 tensor。绝不能靠 RPC 改字符串。

## 2. 大矩阵乘：既不分片也不卸载 —— **相关算子根本不在白名单里**

先纠正一个前提：>60MB 的权重在你们这条链路上**没有走真算**，所以不存在"怎么处理"的问题。

**MoE 部分（35B-A3B 的绝大部分参数）完全没接**：vllm_ascend 的 MoE FFN 用的是 `torch_npu.npu_grouped_matmul`（[moe_mlp.py:184,229,245,373,392](vLLM-ascend_for_lingqu/vllm_ascend/ops/fused_moe/moe_mlp.py:184)）+ `npu_moe_init_routing_v2` / `npu_moe_finalize_routing`。对应的 `aclnnGroupedMatmul*`、`aclnnMoeInitRouting*`、`aclnnMoeFinalizeRouting*` **一个都不在你的 `real_calculation` 列表里**。它们走 original 分支 = stream 模块直接 `return SIM_OK`、不碰输出（[sim_services.cpp:412-424](vAscend/src/stream/sim_services.cpp:412)）。专家权重从头到尾没离开过仿真侧，因为没人要它。

同理 GDN 层：`fused_recurrent_gated_delta_rule_pytorch` 那套 PyTorch fallback 在 npu device 上分解成一堆 aclnn 算子（bmm→`aclnnBatchMatMul`、cumsum、exp…），白名单里也没有。

**换句话说**：Qwen3.5-35B-A3B 的两大主干（MoE FFN + GDN 线性注意力）当前都是零计算。白名单覆盖的是 embedding、rmsnorm、dense matmul/addmm、rope、swiglu、FIA、scatter、argmax 这条"骨架"。**即使 KV 布局问题修好，输出也不可能对**。

**至于真的被白名单覆盖的大 GEMM**（`aclnnMatmul` / `aclnnAddmm` / `aclnnEmbedding`），设计上的答案是：**整块 storage 一次性搬运，没有分片、没有 streaming、没有压缩**——unary 同步 RPC，"第一版不启用压缩"（[rpc_transport.md:703](vAscend/docs/design/modules/real_calculation/rpc_transport.md:703)）。限额：

| 项 | 默认 |
|---|---|
| request / response | 64 MiB |
| **单个 `Tensor.storage`** | **64 MiB** |
| `REAL_CALC_MAX_MESSAGE_BYTES` | 67108864，可调到 2GiB-1 |

（[rpc_transport.md:611,863-872](vAscend/docs/design/modules/real_calculation/rpc_transport.md:863)）超限就是 `MESSAGE_TOO_LARGE`，而且**明确不降级、不重试**（"错误返回非零，不自动降级或重试" [mock_opapi.md:34](vAscend/docs/design/modules/real_calculation/mock_opapi.md:34)、":464"）——硬错误直接抛给 op-plugin，不会静默回落到零计算。

**这里有个矛盾值得你注意**：TP=1 下 `lm_head` / embedding 表是 `vocab × hidden × 2B`，Qwen3 词表 151936、hidden 2048 就是 **622MB**，超 64MiB 上限约 10 倍；而 `aclnnEmbedding` 和 `aclnnMatmul` 都在你的白名单里。按 V2 设计这一步应该直接失败，但你们 prefill 跑通了。只有三种可能：

- 你们部署的 `libcust_opapi.so` 不是 V2 设计（它对应的是 `op_offload_design.md` 里那个简单协议 `rpc op_request(OpDef) returns (OpResult)`），不做这些校验；
- 消息上限被调大了；
- **每个 tensor 只发了前 N 字节**——这就回到 `real_data_size: 8192` 的嫌疑。

**一条命令就能定性**：把 runner 的 REQUEST 日志按算子看请求字节数。

```bash
grep -E 'Got request|REQUEST' runner.log | head -50
```

如果 `aclnnMatmul` / `aclnnEmbedding` 的请求只有几 KB 而不是几百 MB，说明数据在源头就被截断了，真算全程在算噪声——这比 KV 布局问题更致命，而且能一次性解释所有"数值不可信"现象。

**顺带两个配置漂移**（对照交接文档 10.2 那个"三份 SO"教训）：你贴的 `simulator_config.json` 里是 `aclnnFusedInferAttentionScoreV4`，但交接文档说接的是 **V5**；且 `bad_origin` 是空串，而文档说 Scatter/V5/Unique 都需要放进 `bad_origin` 来阻止本地 CANN 先执行。这两处如果是当前真正生效的配置，本地 original 会先跑一遍，正是当初 SIGSEGV / tiling-key 那一类问题的来源。

**如果确实想让大 GEMM 真算**，按收益排序：① 在 runner 侧做**权重驻留**（按内容 hash 缓存 device buffer，跨请求复用）——现在每次调用都重传同一份权重，这才是 13 分钟 TTFT 的大头，但它和现有"ExecutionContext 请求内分配释放"的无状态设计冲突，需要改协议；② 两侧同步调大 `REAL_CALC_MAX_MESSAGE_BYTES`；③ 用 TP 分片让单 rank 权重降到限额内（但跨卡通信是假的，见上一轮结论）。

## 3. 各仿真 rank：**进程完全隔离，buffer 不可跨进程寻址**；是否同主机则不受约束

**不可跨进程寻址，这一点没有回旋余地：**

- 整个仿真状态是**进程内**的：`halDeviceOpen` 时在本进程构造 MemManager、SqCq/Res/Sync 管理器、Resource Register 区（[architecture.md:356-372](vAscend/docs/design/architecture.md:356)）。每个 vLLM worker 进程有自己的一整套"设备"。
- RealMem 后端：`aligned_alloc` + `mmap(MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE)`（[real_mem_backend.cpp:194-195](vAscend/src/mem/backend/real_mem_backend.cpp:194)）——私有匿名映射，进程外不可见。VirtualMem 后端更彻底：数据在进程内的 `std::map<uint64_t,uint8_t> dataMap` 里，别的进程连地址空间都是各算各的。
- `src/` 里**没有任何** `shm_open` / `MAP_SHARED` / `shmget` / IPC handle。
- HAL 对外符号面根本没有 IPC 能力：`halMemAlloc/Free/Memcpy/HostRegister/AddressReserve/Create/Release/Retain/Map/Unmap/SetAccess/GetAddressRange/GetInfo`（[hal_mem.cpp](vAscend/src/frontend/hal_mem.cpp)）——有完整 VMM，但**没有 export/import shareable handle**。跨进程共享 device 内存在这套 HAL 上连表达都表达不出来。

**是否同主机：不要求，设计上就是跨主机的。** dayu 身份是 `idCard = (本机IP << 32) | PID`（[IDCardGenerator.cpp:109-113](vAscend/src/hccl_mock/src/backend/vccl/dayu_sim/IDCardGenerator.cpp:109)），注册时上报 `deviceCount`（VNODE_CARD_NUM=本服务器卡数）、`usedCardNum`（本 PD 实例卡数）、`cardType`（区分 P/D 角色），全部汇聚到远端 dayu server（你配置里的 `141.61.77.46:32355`）。所以千卡可以任意铺在多台机器上，同不同主机对仿真语义没有影响。

**推论（对你们排查有用）**：

1. 同主机的两个 rank 之间**也**只能走 dayu socket，同样受 ≤512B / AllReduce <100B 的截断限制。"反正同机，让它们直接读对方 buffer"这条路不存在。
2. 真算无法跨 rank 去重：同一份权重，同主机上 8 个 rank 就要各自 D2H、各自编码、各自发 8 遍给 runner。runner 的去重只在**单个请求内**按 `storage_id` 生效（[npu_backend.md:326](vAscend/docs/design/modules/real_calculation/npu_backend.md:326)）。
3. 你配置里的 `"using_shared_checkpoint": "false"` 看名字正是唯一可能打破这个隔离的机制（同主机多 rank 共享权重/checkpoint 存储）——**但这套源码里没有它的实现**，而且当前是关的。如果千卡仿真要在有限主机上铺开，这个开关的真实语义值得你们去内网源码确认，它直接决定单机能塞下多少个 rank。

---

三个问题里，第 2 条的结论最需要你们决策：**MoE 和 GDN 不在白名单，当前这条链路在架构上就不可能产出正确输出**。在补白名单（`aclnnGroupedMatmul*` + routing 系列，且它们的权重远超单 tensor 限额）之前，继续调 KV 布局和数值一致性的收益有限。建议先跑那条 runner 请求字节数的 grep——它几分钟就能告诉你是"传了真数据但布局错了"还是"压根没传真数据"，这两种情况后续的路完全不同。
